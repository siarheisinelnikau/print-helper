# Architecture

## Document model

`layout.rs` contains a serializable project recipe: explicit format version, paper settings and ordered page records. Source records contain canonical paths, SHA-256, source page index and native dimensions in points. Crops are fractions of original edges, followed by clockwise quarter turns. N-up cells are row-major. A single `fit` calculation centers each page inside a cell without changing aspect ratio. All margins and gaps are in millimeters, converted through 72 PDF points per inch.

`document.rs` owns immutable image/Windows PDF sources. It bounds actual file reads, rejects oversized files/images, applies EXIF orientation, composites alpha over white and validates saved recipes against source hashes/dimensions. Images are cropped in original pixels before any resampling. Fractional image boundaries expand to the nearest enclosing source pixels to keep tiny crops nonempty. PDFs are loaded from in-memory streams; sources are never opened for writing. Windows PDF sizes are in 96-DPI device-independent units and are converted to points with a 0.75 factor. PDF render requests account for crop before selecting the full-source bitmap dimensions and enforce a raster budget before entering WinRT. The native engine's default page background is white.

`output.rs` creates sheets through one common rasterizer. Preview requests a roughly 1000-pixel longest edge; export/print select 150/300 DPI. Each sheet is generated independently. A minimal PDF 1.4 writer stores sheets as losslessly deflated RGB Image XObjects, includes explicit MediaBox dimensions and a complete xref table, and retains at most one sheet's image/compression data. Files are written to unique adjacent temporary files and flushed before Windows MoveFileEx without REPLACE_EXISTING publishes them. Existing source/output files survive save failures and cancellation. The non-Windows library fallback uses no-overwrite hard links; the application is supported on Windows only.

`printing.rs` opens PrintDlgW only for an explicit Print action. It checks physical dimensions against the layout (six-point tolerance) and driver hard margins before StartDocW. It draws top-down 32-bit DIBs to the physical paper coordinate system, offsetting the printable-area origin, and releases HDC/global dialog resources through RAII. Failures/cancellation call AbortDoc for the current job. Driver copies/collation use PD_USEDEVMODECOPIESANDCOLLATE. No printer or system defaults are changed by the app directly. Driver-specific dialog and spooler effects require manual testing.

## UI and work lifecycle

`main.rs` constructs the egui interface independently of a GPU framework. `native.rs` hosts it with winit 0.30.13 and egui-winit 0.33.3. Input, IME, clipboard, cursor, URLs, DPI information and root viewport commands use egui-winit. The supported application has one native window with embedded egui dialogs; it does not expose secondary native viewports or native screenshot commands. The page list is virtualized. Preview revisions discard stale results; undo/redo keep 64 recipe snapshots and the thumbnail cache is capped at 600 textures.

Two persistent workers use one-command and four-event bounded queues. `BackgroundWake` coalesces independent event-loop notifications, so results and explicit shutdown commands remain deliverable while no egui frames run. This avoids relying on egui's already-pending repaint flag while hidden. The host processes worker results separately from UI layout. Close/unsaved decisions are also dispatched independently of painting. Worker threads block on receive when idle.

`design.rs` centralizes light-surface, ink, muted-text, teal-accent, selection, border and error roles, along with typography and spacing. The toolbar prioritizes Add files and Export PDF; recipe actions live in File. The right panel groups paper/orientation, N-up, dimensions and output quality. Crop controls and printer guidance expand on demand. Settings keeps updates and input/output limits together, shows download progress and offers cancellation only during a download. A failed preview gets a retry state rather than an indefinite loading label. PrintHelper remains a document editor, without a tray workflow. These source-level design changes have not been visually rendered or interactively verified in this no-GUI session.

File dialogs, PDF/image reads, thumbnails, sheet rendering, export, printing, settings writes and update HTTP/download work execute outside the UI thread. Native PDF operations run in an initialized MTA. Import/open is transactional: a failed/cancelled batch does not replace the active catalog/project. Catalog source cost is limited to 256 MiB, excluding opaque native renderer allocations. Deleting pages retains loaded sources for undo; New/Open releases the previous catalog. Application close cancels worker work; there is no tray or hidden background service.

`dialogs.rs` runs all four file-picker actions (input documents, open layout, save layout and export PDF destination) on a fresh, explicitly initialized STA thread. The bounded document worker waits for that short-lived thread and then resumes PDF work in its original MTA. Only paths cross the thread boundary. COM initialization is balanced by a thread-local RAII guard, including panic unwinding; thread/startup failures propagate to the normal error result. Calling rfd directly from the MTA worker previously failed its STA initialization and was silently reported as cancellation. A regression reproduces that exact HRESULT and verifies the isolated STA path without constructing or showing a picker. The COM threading rule is documented in [Microsoft's CoInitializeEx reference](https://learn.microsoft.com/en-us/windows/win32/api/combaseapi/nf-combaseapi-coinitializeex).

## CPU rendering and presentation

`software.rs` wraps egui_software_backend 0.0.2 in a BGRA framebuffer. Shapes are tessellated and rasterized entirely on the CPU. Native presentation copies 0x00RRGGBB pixels to softbuffer 0.4.8, whose Windows implementation uses a GDI DIB and BitBlt. No OpenGL context, glutin, glow, wgpu or DirectX UI presenter is compiled into the Windows dependency graph. This does not disable the Windows compositor or make claims about internals of the OS PDF engine.

The library's internal mesh cache is disabled: an in-memory regression demonstrated that 0.0.2 reuses stale rasterized meshes when only texture contents change. The host still retains a complete last bitmap, so an unchanged OS exposure requires only presentation, without egui layout/tessellation/rasterization. Texture uploads/frees are retained if a prepared frame is suppressed by a hide/minimize transition; hidden worker updates remain in egui's texture manager until the next visible frame. Font-atlas retention, partial texture updates, frees, color order and framebuffer resizing are covered by headless tests.

`RepaintSchedule` coalesces invalidations and deadlines. It uses Wait or the next useful WaitUntil, never Poll. A queued OS redraw suppresses an already expired timer; hidden/minimized/occluded/suspended windows keep dirty state but provide no UI timer. Restore marks the scene dirty once. The framebuffer budget is 16 megapixels, and the native client-size maximum is 4000×4000 physical pixels. Oversized/transient invalid sizes suppress drawing instead of destroying application state. Only the CPU rasterizer dependency receives a development optimization override, as required by its upstream implementation.

Framework-level idle CPU, presentation latency, DPI compatibility, close decisions and restore behavior still require observation. `--render-diagnostics <new-file.json>` records aggregate UI/raster/present counts, exposure blits, suppressed redraws, wakeups and maximum per-stage times on exit. No GUI, self-capture or diagnostic launch was executed in this session; the runtime rendering/load gate remains incomplete. Source inspection, headless raster tests and a GPU-free PE import table do not establish measured idle load or visual correctness of the complete application.

## Update boundary

`updater.rs` uses anonymous HTTPS, including redirects, to one canonical repository's latest published stable release. It compares SemVer precedence independently of build metadata, validates exact asset names/URLs, bounds downloads and actual executable reads to 200 MB, and checks declared size, SHA-256, PE32+ GUI headers, section ranges and entry point. Startup checks are optional/persisted. No installer helper starts before an explicit user action.

`updater/install.rs` separates the file transaction from process control. After confirming parent exit, the helper flushes a separate backup, seals/closes staging files, and replaces the destination using Windows ReplaceFile. Replacement or new-process creation failure restores the original contents before returning an error. A verified original is relaunched only after parent exit; invalid arguments and wait failures never launch an unchecked target. Early helper errors may be written to an adjacent `.error.txt` report. Installation does not modify settings, source documents or recipes. Synthetic-file tests run real Windows file replacement/rollback with fake restart callbacks; no downloaded/replacement executable or updater helper is executed. The Windows operation is based on [Microsoft's ReplaceFile documentation](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-replacefilew), including its partial-failure cases; the independent backup supports recovery from those cases.

The SHA-256 digest authenticates bytes relative to GitHub HTTPS metadata, not an independent publisher signature. Authenticode signing and release publication are not configured in this phase.
